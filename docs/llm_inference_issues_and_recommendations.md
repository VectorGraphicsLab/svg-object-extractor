# Инференс LLM по маскам SVG: найденные проблемы и как лучше строить оценку

Протокол численного и визуального сравнения для **DINO-бейзлайна** по видам аннотаций и артефактам превью: **`docs/gt_baseline_metrics.md`**.

Документ обобщает наблюдения по прогону **structured output** через OpenRouter (`mask_<annotation_id>` на группу аннотаций одного `svg_id`) и сопоставляет их с тем, как устроен **бейзлайн DINO + сегментатор + prune** (`svg_gt_baseline`, см. `baseline_gt_dataset_inference.md`). Цель — зафиксировать расхождения протоколов и предложить практичные улучшения для следующих итераций LLM-экспериментов.

---

## 1. Контекст двух протоколов

| Аспект | LLM (OpenRouter, structured JSON) | Бейзлайн (GT batch) |
|--------|-------------------------------------|----------------------|
| Гранулярность запроса | Один HTTP-запрос на **все** строки датасета с данным `svg_id`; модель видит **все** `(annotation_id, prompt, kind)` сразу | На каждую строку JSONL: свой цикл по `prompt_texts`; **изолированный** текст в DINO для этой строки |
| Формат предсказания | Ровно **один** бинарный вектор длины `node_count` на пару `(svg_id, annotation_id)` | На строку: **0…K** записей — по числу боксов DINO плюс случай **ноль боксов** (отдельная запись); явные `dino_box_index`, координаты |
| Совместимость с метриками «один pred на одну GT-строку» | Прямая: один вектор ↔ одна golden-маска | Нужен **второй слой**: выбор бокса / matching / IoU-argmax / только combined и т.д. |

Подробности бейзлайна — в `docs/baseline_gt_dataset_inference.md` (§2–§4).

## 2. Проблемы и ограничения LLM-прогона

### 2.1. Утечка контекста между задачами на одном SVG

В одном ответе модель получает список всех аннотаций с тем же `svg_id` и должна вернуть поля `mask_<id>` для каждой. Это полезно для согласованности («не назначить одну и ту же ноду двум разным окнам»), но одновременно:

- меняется **задача** по сравнению с изолированным промптом (как у человека или у DINO на одной строке);
- для `one_visible_of_many` с **одинаковым** текстом промпта на одном файле различение идёт только по контексту списка задач — это сложнее, чем когда каждая строка данных задаётся отдельно.

**Риск:** метрики LLM измеряют не «понимание одного объекта по одному запросу», а «совместное заполнение таблицы масок».

### 2.2. Несопоставимость «в лоб» с выходом DINO-бейзлайна

- У успешного LLM-ответа: фиксированно одна маска на `annotation_id`.
- У бейзлайна: несколько кандидатов по боксам или ноль боксов.

Сравнивать только длины файлов предсказаний или считать «не хватает строк» бессмысленно: это разные **семантики артефакта**, а не баг одной из сторон.

### 2.3. Хрупкость длинных structured JSON

На больших SVG и многих аннотациях в группе ответ становится большим. В зафиксированном прогоне (см. `reference/openrouter_structured_run_README.md` в бандле) у одной из моделей были **частичные сбои парсинга** (`Expecting value…`) на нескольких SVG — то есть провал не семантики, а **доставки валидного JSON**.

### 2.4. Качество масок при формально валидной схеме

Schema (`minItems`/`maxItems` = `node_count`, только 0/1) гарантирует длину и тип элементов, но **не** семантику. Пример из того же отчёта: для одной и той же golden-маски одна модель попала точно, другая «раздула» маску (лишние единицы на соседних нодах). Это типичная ошибка **жадного захвата группы** или путаницы порядка обхода DOM.

### 2.5. Расхождение растрового и векторного мира

LLM в эксперименте опирается на описание структуры / порядка нод (и при необходимости на текст SVG), а бейзлайн явно считает **растр** и маски в пикселях, затем проецирует на листья. Разные источники сигнала → разные типы ошибок (геометрия vs логика групп в дереве).

### 2.6. Стоимость и латентность

Один запрос на SVG с большим контекстом и длинным completion дороже и дольше, чем серия коротких изолированных вызовов (или чем локальный DINO после кэширования растра). Для ночных прогонов это влияет на бюджет и retry-политику.

## 3. Рекомендации: как лучше делать дальше

### 3.1. Протокол оценки — явно зафиксировать «что измеряем»

1. **Joint vs isolated:** отдельно репортить метрики для режима «один запрос на SVG» и для абляции «один запрос на `(svg_id, annotation_id)`» — иначе числа нельзя интерпретировать при сравнении с DINO.
2. **Matching-слой для бейзлайна:** перед сравнением с golden одной строкой выбрать одну из предсказанных масок (например argmax IoU по `pred_mask` при наличии нескольких боксов, или отдельная строка для `pred_mask_combined`) и описать это в отчёте.
3. **Стратификация по `annotation_kind`:** как в отчёте OpenRouter — отдельно `exactly_one_visible_object`, `multiple_visible_objects`, `one_visible_of_many`; для последнего особенно важны joint/isolated и качество различения при одинаковом тексте промпта.

### 3.2. Укрепление LLM-инференса

1. **Retry и валидация:** повтор запроса при невалидном JSON; опционально уменьшение размера группы (меньше `annotation_id` на один вызов) для снижения доли обрывов completion.
2. **Два этапа:** сначала короткий ответ (выбор candidate node ids или частей SVG), вторым запросом — двоичный вектор фиксированной длины; иногда стабильнее одного гигантского JSON.
3. **Канон порядка нод:** в промпте жёстко повторить правило соответствия индексам в маске тому же обходу дерева, что в экспорте сервиса (и совпадающему с бейзлайном).

### 3.3. Сравнение с бейзлайном по смыслу, не по формату файла

Иметь общий **evaluation notebook/script**, который:

- читает GT JSONL;
- для LLM: одна маска на строку;
- для NDJSON бейзлайна: агрегирует по ключу `(annotation_id, detector_id, segmenter_id)` с правилом выбора одной маски для метрики;
- считает те же micro/macro IoU / F1 / exact match.

## 5. Краткий вывод

LLM structured batch по SVG даёт **удобный** один-в-один интерфейс к метрикам «одна маска на аннотацию», но вводит **joint reasoning** и **JSON-хрупкость** на больших ответах. Бейзлайн DINO+SAM честнее разделяет **изолированные текстовые запросы** и **мульти-кандидатную** природу детекции, но требует явного **matching** перед тем же видом метрик. Для честного сравнения методов нужно явно описывать оба протокола и при необходимости добавлять симметричные абляции (joint/isolated; один бокс vs combined).
