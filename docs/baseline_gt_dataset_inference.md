# Бейзлайн DINO + SAM (и box-fill) по GT-датасету: инференс и сохранение результатов

Документ фиксирует договорённости для **пакетного инференса** по строкам экспорта (JSONL в стиле `svg-gt-annotation-service`). Концепт замеров (что с чем сравнивать по **`annotation_kind`**, какие превью использовать) — в **`docs/gt_baseline_metrics.md`**; офлайн-скрипт агрегации может подключаться поверх **`predictions.ndjson`** отдельно.

---

## 1. Цель этапа

- Прогнать **растр + Grounding DINO + сегментатор** по тем же SVG и тем же текстовым запросам, что в датасете.
- Сохранить **достаточно данных**, чтобы:
  - не перегонять тяжёлые модели ради смены постобработки или метрик;
  - разбирать краевые случаи (**в т.ч. ноль боксов** у DINO).
- Охватить **четыре конфигурации**: два размера DINO × два сегментатора (см. §7).

### Откуда брать SVG (`object_key` не обязателен для пути)

В экспорте есть и `svg_id`, и `object_key` (ключ в MinIO). Для **локального** прогона по распакованной библиотеке достаточно:

- каталог с SVG + **`svg_archive_manifest.json`** (как в `svg_annotation_library.zip`): по **`svg_id`** найти запись и взять **`filename_in_archive`** (обычно `{svg_id}.svg`, но опираемся на манифест, а не на догадку);
- либо заранее согласованная схема `library_root / f"{svg_id}.svg"`, если гарантируете ту же упаковку.

**`object_key`** оставляем в сохранённых строках как **идентификатор из датасета** (связь с сервисом, диффы, поиск в MinIO), но **не** как единственный способ найти файл на диске.

### Порядок прогона (оптимизация: DINO на детектор общий, сегментаторы навешиваются)

Четыре «варианта» в логе отчёта — это `gdino-tiny`/`gdino-base` × `box-fill`/`sam-vit-base`, но **не обязано** быть четырьмя полными независимыми проходами сверху донизу.

- **Растр** одного и того же SVG для одного `dpi` можно считать **один раз** на `(svg_id)` (или на байты файла) и переиспользовать для всех промптов и детекторов, пока на диске тот же файл.
- **Кэш DINO** (как в §10): ключ уже включает `detector_id`. Для фиксированного **`(svg, detector_id, пороги, dpi, prompt_text)`** — **один** вызов детектора → список боксов.
- **Два сегментатора на те же боксы:** после одного такого DINO для `gdino-tiny` последовательно (или при достаточной памяти с переключением весов) гоняем **`box-fill`** и **`sam-vit-base`** на **одних и тех же** `ctx` + `detections` — это два артефакта без второго DINO-tiny. Аналогично для **`gdino-base`**.

Итого по стоимости нейросетей на уникальный кэш-ключ: **2× DINO** (tiny и base) + **4× сегментация** (две пары на два набора боксов), а не **4× (DINO+сегментатор)**. Порядок внутри реализации: напр. для каждого ключа сначала оба сегментатора с tiny, потом оба с base — или сначала все tiny по всем ключам, потом все base; выбирается по удобству выгрузки весов на GPU.

В выходном NDJSON по-прежнему **четыре** явных набора полей / подкаталога по паре `detector_id` + `segmenter_id`, чтобы потребители не парились с группировкой.

## 2. Связь с текущим пайплайном (`svg_segmentator/pipeline.py`)

После одного вызова DINO сегментатор возвращает список масок по боксам; дальше:

- **Сводный прогон:** `seg.combined_mask` (объединение масок по боксам внутри одного запроса) → один prune → `*_extracted.svg` в корне `out_dir`.
- **По каждому боксу отдельно:** цикл `for idx, (obj_mask, box) in enumerate(zip(seg.masks, detections.boxes))` → подкаталоги `objects/object_{idx:03d}_.../` со своим `obj_mask`, своим prune и своим extracted SVG — это и есть «**каждый объект отдельно**» для сохранения предсказаний.

Для GT-инференса **не** делаем побитового **ИЛИ между разными промптами** в одну запись: каждый элемент `prompt_texts` — отдельный вызов DINO; внутри одного вызова при **K боксах** — **K отдельных сохранённых** `pred_mask` (аналог **K строк** в духе `objects/`, плюс явный `dino_box_index` / координаты бокса). Одна строка датасета с golden `binary_mask` при этом может иметь **0, 1 или много** соответствующих предиктивных записей (в т.ч. 0 при нуле боксов — одна запись со статусом).

**Итог:** выходной JSONL/NDJSON **не** изоморфен LLM-формату «ровно одна маска на `annotation_id` в ответе на весь SVG»; у бейзлайна гранулярность **промпт × бокс** (и отдельно при желании снимок сводного прогона для отладки).

---

## 3. Типы аннотаций (`annotation_kind`) — только смысл для трактовки метрик позже

На этапе инференса **алгоритм один**: для строки датасета, для каждого `prompt_texts[i]` — DINO→SAM/box-fill→prune по каждому боксу как в §2. Различие `exactly_one_visible_object` / `multiple_visible_objects` / `one_visible_of_many` влияет на то, **как потом** сопоставлять множество предсказаний с одной golden-маской (matching, выбор лучшего бокса, отдельные подзадачи) — не на обязательное слияние масок при сохранении.

Пример из датасета: для `one_visible_of_many` с одним промптом «window» на одном SVG существует **несколько** строк с **разными** `annotation_id` и **разными** масками (разные окна) — у LLM это были разные ключи `mask_<id>` в одном ответе; у бейзлайна будут разные прогоны с привязкой к каждой строке и своему набору боксов.

## 4. Текст в DINO и расхождение с LLM-прогоном (OpenRouter)

**Бейзлайн:** каждая строка `prompt_texts` — отдельный запрос к DINO (`query_to_candidate_labels` как сейчас).

**LLM (`run_svg_mask_openrouter.py`):** один HTTP-запрос на группу аннотаций с одним `svg_id`; в `response_format` — обязательные поля `mask_<annotation_id>` для **каждой** строки группы за раз. Модель видит все задачи и все промпты одновременно.

**Что из этого следует:**

- Сравнивать «в лоб» только размеры файлов предсказаний бессмысленно: у LLM **ровно одна** разобранная маска на пару `(svg_id, annotation_id)` в успешном ответе; у DINO на ту же пару может быть **несколько** кандидатов (по числу боксов) или **ноль**.
- Для `one_visible_of_many` с **одинаковым** текстом промпта на одном файле LLM обязан различить контекст по списку задач в промпте; DINO на каждой строке датасета вызывается **изолированно** — риск «всегда детектить одно и то же окно» выше, зато нет утечки подсказок между `annotation_id`.
- Метрики у OpenRouter считались как **один вектор pred на одну GT-строку**; для бейзлайна понадобится **второй слой** (Hungarian / argmax IoU / «только combined» и т.д.) — это сознательно **после** сохранения артефактов.

Развернуто про проблемы LLM-протокола и рекомендации: **`docs/llm_inference_issues_and_recommendations.md`**. Сопоставление с замерами бейзлайна: **`docs/gt_baseline_metrics.md`**.

## 5. Параметры по умолчанию (как в репозитории сейчас)

Брать те же дефолты, что в корневом `README.md` / `PipelineConfig` и скриптах:

| Параметр | Значение по умолчанию |
|----------|------------------------|
| DPI (только если тянем SVG в растр без явного max-side) | `96` — для **GT-батча** см. §5.1: приоритет **фиксированный max-side**, не DPI. |
| `box_threshold` | `0.35` |
| `text_threshold` | `0.25` |
| `score_threshold` (leaf prune τ) | `0.8` |
| `max_leaves` | `0` (без лимита) |

### 5.1 Рабочий растр (один раз на SVG, фиксированный размер)

- Из файла SVG строим **один** RGB-растр в **рабочем** разрешении для **всего** последующего (DINO, SAM/box-fill, leaf masks в пикселях): уменьшение с сохранением пропорций так, чтобы **max(w, h) = 640** px (LANCZOS), unless overridden.
- **Leaf cache / prune** используют **тот же** `rgb_full`, что и детекция (никакого второго растра с другим DPI).
- **Про «стандарт по DINO»:** в текущем `gdino_hf.py` в детектор уходит PIL как есть; внутри `AutoProcessor` чекпойнта свой resize (часто ориентир порядка **~800** px по большей стороне в `preprocessor_config` у IDEA/MM весов — см. файлы конфига на Hugging Face). **640** — сознательно более лёгий и быстрый канон для **нашего** батча и кэша; если понадобится ближе к типичному eval — поднять константу до **800** одним параметром.
- Ключи кэша и сохранённые метаданные должны включать **`raster_max_side`** (и хеш/путь исходного SVG), чтобы смена размера не смешивала старые артефакты.

### 5.2 Фильтр строк датасета

- Строки с **`review_decision == "declined"`** в прогон **не** включаем.
- Остальные (`null`, **`approved`**) — в общий прогон; при офлайн-анализе можно ещё сузить до только `approved`.

### 5.3 Smoke

- Перед полным прогоном: режим **smoke** — только **первые три уникальных `svg_id`** среди отфильтрованных строк (порядок как в JSONL), полный пайплайн с логом и проверкой NDJSON/кэша.

## 6. Что сохранять (максимум полезной инфы, без CLIP)

**CLIP в артефакты не пишем** (ни сводный, ни по объектам) — инференс легче и проще.

Для **каждой** сохраняемой предиктивной записи (промпт × бокс, плюс явный кейс «ноль боксов»):

- Провенанс из датасета: `svg_id`, `annotation_id`, `annotation_kind`, `object_key`, `original_filename`, `node_count`, golden `binary_mask` (копия из строки датасета).
- Привязка к подпрогону: `prompt_index` (индекс в `prompt_texts`), строка `prompt_text`, `dino_box_index` (0…K−1 или `null` при `n_boxes==0`).
- Детекция: `n_boxes`, боксы (xyxy, score, label), флаг `zero_boxes`.
- Сегментация: по желанию путь к PNG `query_mask` / размеры растра; **без** вызова `clip_image_text_score`.
- Маска в тегах: `pred_mask` длины `N` после prune для **этого** бокса (как в `objects/object_*/`); при нуле боксов — нулевой вектор длины `N` и/или `status: no_detections`.
- **Обязательно** в той же записи: `pred_mask_combined` — prune по `combined_mask` того же DINO-вызова (одинаковое для всех строк с одним `(annotation_id, prompt_index)`; при `n_boxes==0` — нули длины `N`).

Каталог: общий корень прогона → подкаталог `detector_id` × `segmenter_id` → NDJSON/JSONL **на каждую сохранённую запись** (не обязательно 1:1 со строкой датасета).

**Датасет:** все строки **после** фильтра §5.2 (без `declined`); дополнительные фильтры — офлайн по полям в артефакте.

### 6.1 Промежуточные файлы на диске (resume после падения)

Чтобы при обрыве не гонять заново тяжёлые стадии:

- **Растр:** `cache/raster/{svg_content_hash}_m{raster_max_side}.png` (или аналог) — если файл есть, не растеризовать SVG снова.
- **DINO:** `cache/dino/{dino_cache_key_hash}.json` — сериализованные боксы, скоры, лейблы, размер рабочего RGB; при попадании — не вызывать детектор.
- **Сегментация (опционально):** крупные тензоры/PNG по ключу `(dino_cache_key, segmenter_id)` если нужно отлаживать без повторного SAM.
- **Финальный NDJSON:** дописывать **по одной записи с flush**; вести `cache/progress.json` (или append-log) с последним успешно обработанным ключом / счётчиком для мониторинга.
- При старте: если для `(dino_cache_key, segmenter_id, annotation_id, prompt_index, dino_box_index)` запись уже есть в выходном NDJSON — **skip** (идемпотентный рестарт).

## 7. Четыре варианта запуска (матрица)

Сегментаторы в реестре: `box-fill`, `sam-vit-base`. Детекторы для матрицы «малый / нормальный» DINO:

| # | `detector_id` | Сегментатор |
|---|----------------|-------------|
| 1 | `gdino-tiny` | `box-fill` |
| 2 | `gdino-tiny` | `sam-vit-base` |
| 3 | `gdino-base` | `box-fill` |
| 4 | `gdino-base` | `sam-vit-base` |

Каждая из четырёх комбинаций — **отдельный** полный прогон по выбранному срезу датасета (кэш весов один раз на пару, по аналогии с `EvalPipeline`).

### 7.1 GPU и порядок загрузки моделей

- **Одна GPU:** по умолчанию **`CUDA_VISIBLE_DEVICES=0`** — одна из двух **3090**; вторая не используется, пока явно не попросят параллель.
- **Порядок (рекомендация):** сначала загрузить и прогнать все кэш-ключи для **`gdino-tiny`** (DINO → оба сегментатора → выгрузить сегментаторы при необходимости), затем **`gdino-base`** тем же образом — меньше пляски с двумя большими детекторами в памяти одновременно.

## 8. Согласование индексов `N` и листьев

- Эталон: `node_count` и порядок узлов как при разборе в GT (DFS pre-order, drawable-листья для единиц).
- В коде сегментатора: `data-local-id` / `seg_<i>` при обходе `root.iter()` — **должен** совпадать с глобальным индексом `i` при том же байтовом SVG.
- **Если** после парса число узлов ≠ `node_count` из строки датасета (или иная явная несовместимость): **пропуск** этой строки с записью в `manifest_skips.jsonl` (или аналог) и **очень заметный** WARN в логе (дублировать в stderr: `svg_id`, `annotation_id`, `object_key`, ожидаемое и фактическое `N`). Не подменять и не дополнять/не обрезать маску принудительно.

## 10. Принятые решения (чеклист)

| Тема | Решение |
|------|--------|
| ИЛИ между промптами в одну запись | **Нет**; каждый промпт — отдельный DINO; каждый бокс — отдельная запись с `pred_mask` (как `objects/` в пайплайне). |
| Ноль боксов | Сохранять явно (одна запись на промпт с `n_boxes=0`, нулевой `pred_mask` и/или `status`). |
| Строки датасета | **Все, кроме `review_decision == "declined"`**; остальное (например только `approved`) — офлайн. |
| `node_count` ≠ парсер | **Skip** + заметный WARN + manifest. |
| CLIP | **Не** считать и не сохранять в этом прогоне. |
| Кэш DINO | **Да:** один вызов детекции на ключ `(идентификация SVG, detector_id, пороги, растр: raster_max_side, текст промпта)`; результаты размножать на строки датасета. **Плюс:** после DINO прогнать **оба** сегментатора без повторного DINO; tiny и base — **два** DINO на ключ. |
| Воспроизводимость | **Фиксированный seed** в начале каждого матричного прогона: `PYTHONHASHSEED`, `torch.manual_seed`, при наличии CUDA — `torch.cuda.manual_seed_all` (конкретное значение по умолчанию, например `42`, с возможностью переопределения CLI). |
| `pred_mask_combined` | **Всегда писать** в артефакт: в каждой записи по боксу дублировать одно и то же поле `pred_mask_combined` (prune по `combined_mask` того же DINO-вызова); при `n_boxes==0` — нулевой вектор длины `N` (согласовано с отсутствием детекций). |
| Рабочий растр | **max(w,h)=640** по умолчанию (§5.1); HF DINO внутри может ещё ресайзить — это отдельный слой. |
| Промежуточные файлы | **Да:** кэш растра, JSON DINO, опционально маски сегментации; NDJSON с flush + идемпотентный skip при рестарте (§6.1). |
| GPU | По умолчанию **одна** карта: `CUDA_VISIBLE_DEVICES=0` (две **3090** — вторая не задействована без явного запроса). |
| Smoke | Первые **3** уникальных `svg_id` после фильтра §5.2. |

## 11. Реализация кэша (уточнение)

- Ключ кэша DINO должен включать всё, от чего зависят боксы: хеш байтов SVG + **`detector_id`** + **`box_threshold`** + **`text_threshold`** + **`raster_max_side`** (рабочий растр §5.1) + нормализованная **`prompt_text`**. (Поле `object_key` из датасета в ключ **не обязательно** — достаточно хеша содержимого файла.)
- Сегментатор на кэш ключа **не** влияет: после одного попадания в кэш DINO для `(svg, detector_id, …, prompt)` последовательно вызываются **оба** сегментатора на **те же** боксы; в NDJSON пишутся строки с разными `segmenter_id`.
- В NDJSON каждая строка по-прежнему привязана к своей строке датасета (`annotation_id`, …), но поля боксов копируются из кэша, если ключ совпал.

## 12. Реализация: пакет `svg_gt_baseline` и CLI

- **Пакет:** `svg_gt_baseline/` — растр (Cairo `output_width` / `output_height`, без PIL-resize после), разбор датасета, кэш DINO на диске, сегментация `box-fill` + `sam-vit-base`, маски в индексах `seg_*`, NDJSON.
- **Скрипт:** `scripts/run_gt_baseline_inference.py` — подставляет корень репозитория в `sys.path`, вызывает `svg_segmentator.repo_env.load_repo_dotenv()` (чтобы из корневого `.env` подтянулся **`HF_TOKEN`** до загрузки моделей); логи `httpx`/`httpcore` при `-v` приглушены.

Пример smoke (артефакты по умолчанию в **`output/gt_baseline/`** в корне репозитория, если не передать `--out`):

```bash
cd /path/to/svg-segmentator
.venv/bin/python scripts/run_gt_baseline_inference.py \
  --dataset "dataset (1).jsonl" \
  --manifest _extracted_20260508/svg_annotation_library/svg_archive_manifest.json \
  --smoke --smoke-n 3
```

Свой каталог: `--out output/my_run` или абсолютный путь.

**Выходы внутри `--out`:** `predictions.ndjson`, `run_config.json`, `run.log` (дублирует лог в консоль, с временными метками), `cache/`, `manifest_skips.jsonl`.

**Картинки:** дерево под `previews/<svg_id>/` (контекст в путях, имена файлов короткие):

```
previews/<svg_id>/
  meta.json
  source.svg
  raster.png
  ann_<annotation_id>/
    meta.json
    gt_mask.png
    gt_overlay.png
    gt_extracted.svg
    gt_extracted.png
    p<prompt_index>/<detector_id>/
      meta.json
      dino_boxes.png
      <segmenter_id>/
        meta.json
        mask_union.png
        extracted_union.svg
        extracted_union.png
        extracted_box0.svg …
        extracted_box0.png …
        ...
```

Файлы не перезаписываются, если уже есть (удобно для resume).

Рядом с картинками пишутся **`meta.json`** (перезапись при каждом проходе): на уровне SVG — id и пути; **`ann_*`** — все промпты строки, GT-счётчики, пороги; **`gt_extracted.svg`** — дерево после prune по **`binary_mask`** (листья с меткой 1 остаются; порог скоринга для prune фиксирован 0.5, т.к. маска бинарная); **`gt_extracted.png`** — тот же вывод, растр Cairo с тем же `raster_max_side`, что и у инференса; **`p*/<detector>`** — текст запроса, `text_labels`, пороги DINO, список боксов, путь к кэшу JSON; **папка сегментатора** — порог prune, пиксели масок, число выбранных листьев, сводка по боксам. В папке сегментатора же лежат **обрезанные SVG** после prune (как в интерактивном пайплайне): **`extracted_union.svg`** / **`extracted_union.png`** по объединённой маске сегментатора и **`extracted_box{i}.svg`** / **`extracted_box{i}.png`** по маске каждого бокса DINO (PNG — Cairo с тем же `raster_max_side`). Дополнительно: **`pred_leaf_mask.png`** — объединение масок листьев для **`pred_mask_combined`** на рабочем растре (для согласованного сравнения с GT-маской листьев). Для **`one_visible_of_many`** после прогона — **`previews/<svg_id>/oom_merged_<slug>/`** (объединённый GT группы) и зеркала **`gt_merged_group_*`** в папках сегментаторов; см. **`docs/gt_baseline_metrics.md`**.

Изменения в **`svg_segmentator`:** `render.svg_bytes_to_png_sized` / `svg_file_to_png_sized`; `extract.build_leaf_mask_cache(..., output_wh=...)` для согласованного размера веток листьев с растром.
